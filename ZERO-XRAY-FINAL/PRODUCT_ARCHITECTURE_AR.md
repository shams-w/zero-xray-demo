# التصور التنفيذي للمنتج — ZERO X-RAY

## الفكرة في جملة واحدة

المنصة تحول وصف أي خدمة إلى **Blueprint قابل للمراجعة والاعتماد**، ثم تعرض
للموظف رحلة المساعد كما سيراها المتعامل، وتسمح بتجربة الطلب والخطة والموافقة
والدفع والتنفيذ في بيئة Sandbox موثقة.

## مساحتا العمل

### 1. استوديو تصميم الخدمة للموظف

1. يكتب الموظف الخدمة أو يرفع ملف PDF أو DOCX أو XLSX أو صورة.
2. تَعرض المنصة البيانات والخطوات المستخرجة قبل التحليل لتصحيحها.
3. يحدد الموظف حماية كل خطوة عند الحاجة:
   - **حماية المتطلب `REQUIREMENT`:** لا يجوز حذف المتطلب، ويمكن تحسين طريقة تنفيذه.
   - **قرار بشري `HUMAN`:** يجب أن يبقى قرار أو تدخل بشري واضحًا في الرحلة.
   - **كما هي `AS_IS`:** تبقى الخطوة بالنص والمعنى الحاليين ولا يحذفها المساعد.
4. يكتب الموظف سبب الحماية والمرجع التنظيمي إن وجد.
5. تحلل المنصة الرحلة الحالية، وتطابقها مع الدليل، وتبني رحلة مستقبلية.
6. تظهر النتائج: الخطوات الحالية والمستقبلية، ما حُذف أو دُمج أو أُتمت، الأثر،
   القيود البشرية، التكاملات المقترحة، وحالة التحقق.
7. تظهر أدلة الدليل الحكومي بأرقام مرجعية وموقع المصدر ونسبة المطابقة.
8. يُحفظ التصميم كـ`DRAFT`، ثم يمر على `APPROVED`، ثم `PUBLISHED`.
9. زر **تجربة رحلة المساعد** يفتح مساحة مستقلة تحاكي رحلة المتعامل.

### 2. ZERO Agent Live Sandbox للمتعامل

1. تسجيل هوية تجريبية بالاسم والبريد.
2. كتابة النتيجة المطلوبة بلغة طبيعية، مثل: «أريد تجديد التصريح».
3. اختيار الـBlueprint المناسب وبناء خطة تنفيذ مرقمة وقابلة للتتبع.
4. عرض الخطة قبل أي دفع، وتشمل:
   - الأعمال التي سينفذها المساعد.
   - دليل إتمام كل عمل.
   - الرسوم ومصدرها، أو تنبيه أنها تحتاج نظام رسوم متصل.
   - المدة المعتمدة، أو تنبيه أنها تحتاج SLA معتمدًا.
   - التكاملات المقترحة والخطوات المحمية.
5. يستطيع المتعامل طلب تعديل؛ تُحفظ نسخة جديدة من الخطة وسجل التعديل.
6. عند الموافقة تنتقل الرحلة إلى دفع Sandbox بموافقة صريحة.
7. يبدأ التنفيذ بعد نجاح الدفع فقط، وتظهر أحداث المساعد مباشرة عبر SSE.
8. يمكن الإلغاء أو التحويل لموظف؛ ولا يكمل النظام الرحلة بعد ذلك تلقائيًا.
9. عند النجاح تظهر النتيجة والمرجع والمدة ومسار الاعتراض في نفس الرحلة.

## حالات الـBlueprint والرحلة

| العنصر | الحالات الأساسية |
|---|---|
| Blueprint | `DRAFT` → `APPROVED` → `PUBLISHED` |
| الخطة | `PLAN_READY` → `PLAN_EDITED` أو `PLAN_APPROVED` |
| الدفع | `PLAN_APPROVED` → `PAID` |
| التنفيذ | `PAID` → `EXECUTING` → `COMPLETED` |
| التحكم | `PAUSED` أو `CANCELLED` أو `HUMAN_HANDOFF` |

## ما نُفذ في النسخة الحالية

- قاعدة SQLite محلية تحفظ Blueprints والعملاء ونسخ الخطط والدفع والأحداث وسجل
  التدقيق.
- واجهات API للتحليل والاعتماد والنشر والتسجيل والخطة والتعديل والموافقة والدفع
  والتنفيذ والتحكم.
- أحداث تنفيذ Live باستخدام Server-Sent Events.
- قيود بشرية لها أولوية على توصية الحذف الآلية.
- استرجاع أدلة من دليل المعايير وإظهار مصدر كل دليل.
- واجهة عربية وإنجليزية، ومسار تشغيل خفيف دون تنزيل نموذج كبير افتراضيًا.

## الحد الفاصل بين العرض والتشغيل الحقيقي

المنصة تستطيع **تحليل وتصميم أي خدمة** من وصفها، لكن تنفيذها فعليًا داخل جهة
حكومية يحتاج Adapters معتمدة لأنظمة تلك الخدمة. لذلك تعرض النسخة الحالية الدفع
والهوية والتنفيذ كـSandbox، وتضع `PROPOSED` أو `SIMULATED` على أي تكامل غير متصل.
هذا يمنع تقديم ادعاء غير صحيح أثناء العرض أو التقييم.

## متطلبات الانتقال إلى إنتاج حكومي

1. ربط الهوية الرقمية، بوابة الدفع، كتالوج الخدمات، الرسوم، الوثائق، والإشعارات
   عبر واجهات الجهة المعتمدة.
2. استبدال SQLite بقاعدة PostgreSQL مُدارة مع تشفير ونسخ احتياطي وإقامة بيانات
   حسب سياسة الجهة.
3. إضافة SSO وRBAC وفصل الأدوار بين المصمم والمراجع والناشر والمدقق.
4. إدارة الأسرار في Vault، تشفير النقل والتخزين، وسجل تدقيق غير قابل للعبث.
5. بوابات اعتماد قبل التنفيذ للأعمال الحساسة، وحدود صلاحيات لكل أداة.
6. اختبارات أمن واختراق وخصوصية، مراقبة وتشغيل، وخطط تعافي واستمرارية.
7. تقييمات جودة للـAgent لكل خدمة: نجاح المهمة، صحة الأدلة، عدم تجاوز القيود،
   سلامة الدفع، وجودة التحويل للموظف.

## قيمة المنتج لجهة تنظيمية

- فصل واضح بين تصميم السياسة وتنفيذ المساعد.
- أثر تنظيمي قابل للتتبع لكل خطوة محمية.
- موافقة صريحة قبل الدفع والتنفيذ.
- لا توجد رسوم أو مدة أو تكاملات مختلقة.
- رحلة موحدة من إعادة هندسة الخدمة حتى تجربة المتعامل الحية.
